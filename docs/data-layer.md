# Data Layer (Dexie / IndexedDB)

## How It Works

- `src/lib/db.ts` -- Dexie subclass + record interfaces, no business logic. `src/lib/routine-store.ts` (import/delete) and `src/lib/session-store.ts` (active session lifecycle) -- all mutations, one transaction per operation.
- Tables: `routines` (pk `id`, index `importedAt`), `progress` (pk `routineId`), `lastUsed` (pk `exerciseKey`), `sessions` (`++id`, indexes `routineId`, `finishedAt`), `activeSession` (pk `id`).
- `activeSession` is a singleton: its only row always has id `"current"` -- one active session app-wide. `startSession` overwrites it EXCEPT when the running session is for the same routine + day, which it leaves untouched so the caller resumes it, `finishSession` archives it into `sessions` (dropping execution-only identity fields), advances `progress` with wraparound, and deletes it.
- `activeSession.postponed` is the queue of postponed item indexes; the effective item order is derived (`pending items in natural order`, with the queue spliced in right before the day's first `cooldown` item, or appended when the day has none), so an absent queue means the natural order. It is not indexed, so it needed no `version(2)`. It is applied only when every entry is a unique valid index of a `work` item -- restricting it to work items is what keeps the landing rule coherent, since a queued stretch would jump ahead of the cool-down and reorder the stretches among themselves. A queue that no longer applies is not silently tolerated: the resume paths (`resolveResumableDay`) reject the session, and `resume-session-prompt.tsx` treats an unresolvable day as orphaned and calls `discardActiveSession()`, deleting the session and every set logged in it. The natural-order fallback inside `initWorkoutState` is defence-in-depth for a session that reached the workout another way, not the live path. The workout owns the queue and `setPostponedItems` persists it whole (never read-modify-write), so the record cannot diverge from the order the plan is built from and a stale queue is repaired by the next postponement.
- `resolveResumableDay` also rebuilds the session's own plan (day + queue) and requires every `completed` entry to still land on the `slotKey` and `setIndex` it was logged against. The day id is not enough once the queue is in play: re-importing a routine with a `phase` added moves where the queue lands, so the same `stepIndex` resolves to a different exercise and the logged sets would be silently reattributed.
- The reorder is legal only at the frontier, on a `work` item's first step, and only for an item that sits before the day's first cool-down. That last condition is not cosmetic: the queue lands ahead of the cool-down, so postponing a `work` item positioned after one would move it *backwards*, below the pointer, where the `completed` entries keyed by `stepIndex` live.
- `activeSession.restEndsAt` (epoch ms) persists the running rest across PWA kills: written by `recordSetCompletion` when a rest follows (and dropped otherwise, so a stale deadline never survives a completion), removed by `clearRest` when the rest finishes or is skipped. On resume the workout enters the remaining rest, or the set directly when the deadline elapsed.
- Day selection and the day overview are read-only. `startSession` runs only from the overview's `Empezar entrenamiento` action, so navigating back never leaves a resumable session behind. The reverse is what the guard covers: back-navigation (or an accidental edge swipe on the phone) puts a running workout's own overview back on screen, and a blind `put` there would drop every logged set. Its action reads `Reanudar entrenamiento` for the running day.
- `lastUsed` and `sessions` are keyed by exercise key and GLOBAL across routines -- they intentionally survive routine deletion.
- Prefill (`resolvePrefill` in `src/lib/session-plan.ts`) splits the two fields by what they mean. Reps and duration are the routine's PRESCRIPTION and always come from the plan -- history never overrides them, so a re-imported phase's rep drop is visible and a bad day's six reps are not tomorrow's target. Weight is the exercise's STATE and comes from `lastUsed`.
- `lastUsed` is exactly one weight per exercise key (`{ exerciseKey, weight?, updatedAt }`). Weight is a PER-EXERCISE value, not a per-set one: the last weight logged is what every one of its sets starts at the next session, so there is nothing per-set left to store. `finishSession` writes the last weight of the session in completion order, and an absent weight (the exercise was logged bodyweight) clears the stored one. The cost: a routine's per-set weight ramp only survives its own session -- the first logged set replaces it.
- Within a session, a logged weight that deviates from its own prefill carries over to the exercise's later sets (session precedent); a confirmed prefill does not, so a planned ramp survives the session it was authored for.
- Schema `version(2)` collapsed the old `lastUsed.sets` array into that single weight, taking the last weight present in the array (`src/lib/db.ts`, covered by `src/lib/db.test.ts`). The upgrade is deliberately self-contained -- a migration is a snapshot of the past, so it must not follow the app's rules as they move.
- Validation (Zod `routineSchema` in `src/lib/routine-schema.ts`) happens before any DB write; error paths must leave the DB untouched.

## Key Conventions (user-decided, do not relitigate)

- Re-importing an existing routine id overwrites the definition but preserves progress, lastUsed, and sessions. If the new version has fewer days than the progress pointer, the pointer resets to 0.
- Deleting a routine removes only its `routines` + `progress` rows.
- Routine list order: `orderBy("importedAt")`, oldest first.

## Gotchas

- The schema is a contract now that there is real data on a real phone: any shape change requires a new `version(n)` with an upgrade function and a test that seeds the previous version and opens `db` (see `src/lib/db.test.ts`). Never edit a shipped version in place.
- `useLiveQuery` returns `undefined` on first render -- components must branch `undefined` (loading) vs `[]` (empty) explicitly.
- Dexie liveQuery observes transactions natively; never add manual state-syncing or refresh logic on top.
- `sessions` and `lastUsed` are both written by `session-store`'s `finishSession` (in its single transaction) -- never write them from UI code directly. `recordSetCompletion` touches only `activeSession`, so a discarded session leaves no trace.
- Reordering the plan (`setPostponedItems`) is legal ONLY when the pointer sits at the frontier on an item's first step. Only then is nothing at or above the pointer completed, so moving whole blocks from the pointer onwards cannot remap any completed entry's `stepIndex` -- which is exactly what keeps `completed`, the progress bar, and the session weight precedent valid. The pointer itself never moves on a postponement; pulling a postponed exercise forward postpones everything scheduled in front of it instead.
- Completed entries retain their planned slot identity (`itemIndex:memberIndex`). At finish, every set in that slot is attributed to the slot's final session alternative, so a mid-exercise swap cannot split history or `lastUsed` across keys.
- `finishSession` resolves the completed `dayId` in the latest imported routine and advances to the following day in that latest order. If the completed day no longer exists, the transaction aborts without archiving, advancing, writing `lastUsed`, or deleting the active session.
- `finishSession` derives `lastUsed` from the normalized completed entries, grouped by final effective key: each group keeps the weight of its last entry BY `completedAt`, not by set index. Going back to correct set 1 after set 2 is therefore what the exercise carries forward -- it is the last thing that was actually lifted.
